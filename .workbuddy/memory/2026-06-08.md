## 编辑器损坏图片重试 + 控制台 500/Timeout 修复（提交?）

### 问题现象
- `persist_1780766318226.jpg` 在模拟器中 500（文件已从沙箱消失）
- 控制台反复出现 `Error: timeout` + 图片 500
- 根因：损坏图片 `onerror` 后 `imageCache` 保留 `loaded:false` 条目，`_drawImage` 每次渲染都返回 pending，导致反复重试甚至 WeChat 内部超时

### 修复
- 新增模块级 `failedImages` Set，记录永久失败的图片 URL
- `loadImage()` 开头检查 `failedImages`，已失败则立即 reject，不触发网络请求
- `loadImage()` `onerror` 时把 src 加入 `failedImages`
- `_drawImage()` 检测到 `failedImages.has(src)` 时显示 `BROKEN` 占位符，不再重试
- `_loadPendingImages()` 跳过 `failedImages` 中的图片
- `imageCache.clear()` → 同时 `failedImages.clear()`
- `_addSavedImageElement()` 已有 `.catch()`，无需改动

## 修复双重 BOM 导致模拟器启动失败（提交 021ffff）

**报错现象**：`[] [object Object](env: Windows,mp,2.01.2510290; lib: 3.16.1) 模拟器启动失败`

**根因**：上次用 Python 脚本修复 bug 时，以文本模式读取再以文本模式写回，导致 `utils/storage.js` 开头产生了**双重 BOM**（`\xef\xbb\xbf` × 2）。微信小程序解析器遇到双 BOM 时会抛出 `[object Object]` 错误并无法启动。

**修复**：以二进制模式读取，剥掉所有 BOM 后写回单个 BOM（标准 UTF-8 with BOM）。

**教训**：用 Python 处理已有 BOM 的 JS 文件时，必须以二进制模式读写，避免 BOM 重复。

## 修复 PC 端 PDF 导出 storage limit 错误

### 问题
电脑端微信 `USER_DATA_PATH` 有 10MB 存储上限，旧 PDF 堆积 + 大体积 JPEG 导致 `writeFileSync` 报 `the maximum size of the file storage limit is exceeded`

### 修复 (pdf.js)
1. **`savePdf()`**: 写入前 `readdirSync` 扫描并 `unlinkSync` 清理所有旧 `.pdf` 文件，释放空间
2. **`savePdf()`**: 改用 `base64ToArrayBuffer` + `writeFileSync(path, arrayBuffer)` 二进制写入，比 base64 字符串写入省约 25% 空间
3. **`canvasToJpeg()`**: JPEG 质量从 0.85 降至 0.6，每页体积缩小约 40%

### 修复抠图保存 storage limit 错误 (ai.js)
- **问题**: 与 PDF 同因，`saveArrayBufferPng` 写 `cutout_*.png` 到 `USER_DATA_PATH` 触发 10MB 上限
- **修复**:
